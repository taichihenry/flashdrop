# FlashDrop · 跨设备互传

**任意两台设备之间传文字、传文件** —— 手机 ⇄ 电脑、手机 ⇄ 手机、电脑 ⇄ 电脑都行。
无论是在同一个 Wi-Fi 下，还是各走各的网络、隔着地域，打开网页就能互传，
**文件在两台设备之间直连传输，不经过任何第三方服务器**。

- **同一个网络**（同一个 Wi-Fi）：打开网页就自动互相「看见」，点一下就能发
- **不同网络**（一台 Wi-Fi、一台流量，或两地相隔）：用 6 位配对码牵线
- **P2P 打不通时**：自动降级到 TURN 中继，再不行还有服务器转发兜底，**保证送得到**

实现参考了 [PairDrop](https://github.com/schlagmichdoch/PairDrop) 的架构（WebRTC + WebSocket 信令），但代码是从零写的，并做了几处针对性改进（见文末「和 PairDrop 的差异」）。

---

## 一、两种用法，先选一个

| 用法 | 适合什么场景 | 入口 |
|---|---|---|
| **① 公网版**（推荐） | 要跟**不在同一个网络**的人互传 —— 跨运营商、跨地域都行 | 部署到 Cloudflare，见 **`docs/Cloudflare部署手册.md`** |
| **② 本地版** | 只在自己家/办公室的同一个 Wi-Fi 内用，不想上公网 | 双击 `start-flashdrop.bat` |

两者**传输能力完全一样**（共用同一套前端代码），区别只有一个：**"牵线人"由谁扮演**。

> ### 先澄清一个最容易误会的地方
>
> **`start-flashdrop.bat` 不是给访客装的程序，它是"启动服务器"的开关。**
> 两种模式下，**访客都不需要安装任何东西** —— 打开浏览器、输入网址就能用。
>
> WebRTC 虽然叫"点对点"，但两台设备在直连之前**互相看不见**（不知道对方的公网地址和端口），
> 必须先找一个**双方都够得着的第三方**帮忙交换这些信息，这一步叫「信令」。
> 文件确实是直连传的，但**牵线这件事必须有人干**：
>
> | | 牵线人是谁 | 你要做什么 | 访客要做什么 |
> |---|---|---|---|
> | **公网版** | Cloudflare（全年在线） | 什么都不用开 | **什么都不用装** |
> | **本地版** | **你自己的电脑** | **双击 `.bat` 把它跑起来** | **什么都不用装** |
>
> **要给用户用，只需要公网版。** 部署完之后你电脑关机、`.bat` 删掉，网站照样跑。
> 本地版是给你自己在家临时用的 —— 因为你没租公网服务器，只能让你这台电脑顶上。
> 详见 **`docs/公网部署与TURN额度.md`** 第一节。

### 1.1 公网版：跨网络、跨地域都能传

部署完成后，**所有人访问同一个网址**（例如 `https://6.中国`）即可：

1. 两台设备各自打开这个网址
2. **同一个网络下**：互相自动「看见」，点一下对方名字就能发
3. **不同网络下**（一台 Wi-Fi、一台流量，或两地相隔）：一端点顶部**配对**，
   拿到 6 位码告诉对方，另一端输码 → 立刻牵上线

> **为什么不同网络要输码？** 服务端按**出口 IP 网段**分房间（这正是"同网络自动发现"的原理），
> 出口 IP 不同自然分进两间房，所以需要一个码把两边拉到一起。详见**第九节**。

### 1.2 本地版：同一个 Wi-Fi 内自用，不上公网

> **这一版不是给用户用的**，是给你自己在家/办公室临时用的（不想把服务放上公网，或只想先试试功能）。
> 因为没部署到公网，**你这台电脑就得亲自当那台服务器**，所以要双击把它启动起来。
>
> 双击 `start-flashdrop.bat` 后它做三件事：找到 Node.js → 首次运行装依赖 → 启动信令服务。
> **只要这个黑窗口不关、电脑不休眠，服务就在**；关掉窗口或电脑重启，网站立刻打不开 ——
> 这就是"你的电脑在当服务器"的含义。

**双击 `start-flashdrop.bat`**，控制台会打印访问地址。

```
┌─ 本机（这台电脑的浏览器）────────────────────
│  http://127.0.0.1:8686
│  https://127.0.0.1:8687
│
├─ 其他设备（需在同一 Wi-Fi 内）───────────────
│  https://192.168.1.5:8687
│  http://192.168.1.5:8686
```

**电脑端**：浏览器打开 `http://127.0.0.1:8686`。

**其他设备**：

1. 连上**同一个 Wi-Fi**
2. 打开上面那串 `https://192.168.x.x:8687`
   （也可以直接扫电脑页面上的二维码，省得手输）
3. 首次会提示「**证书不受信任**」——这是自签名证书的正常现象，点 **高级 → 继续访问**
4. 两端页面会自动互相「看见」，点设备图标即可发送

> **为什么这里必须走 HTTPS？**
> 现代浏览器把 WebRTC 归为高权限 API，只在「安全上下文」里放行。`https://` 和 `http://127.0.0.1` 算安全上下文，但 **`http://192.168.x.x` 不算**。
> 走 HTTP 也能打开页面，只是浏览器会禁用点对点直传，程序会自动降级为「服务器中继」（文件经你本机服务转发，速度慢，页面会提示）。
>
> ⚠️ **本地版有两个硬边界**：① **不能跨网络** —— `192.168.x.x` 这个地址只在局域网内有效；
> ② **本机一关机/休眠，网站就打不开**。要给别人长期使用，请走公网版（1.1），
> 别用"让电脑一直开着"这种办法。

### 本地版用不了？按顺序排查

1. **防火墙**：首次启动若弹出对话框，必须勾选「专用网络」允许。没弹或者点错了，右键以管理员身份运行一次 `allow-firewall.bat`。
2. **确认在同一网段**：手机可能连的是 5G 而不是 Wi-Fi，或者连了访客网络（访客网络通常做了隔离，设备之间互相看不见）。
3. **路由器开了 AP 隔离**：部分路由器/公共 Wi-Fi 会禁止客户端互访，这种网络下 P2P 建立不起来，只能走中继。
4. **换端口**：`start-flashdrop.bat --port 9000`（HTTPS 会自动用 9001）。

## 二、怎么用

### 传文件

1. 点一下目标设备（卡片高亮 = 已选中）
2. 把文件**拖进虚线框**，或点它选择文件（支持多选）
3. 对方页面弹出确认框，点「接受」
4. 接收端自动下载；如果浏览器拦了多个下载，点记录里的「再次保存」

### 传文字 / 网址

在输入框里打字（支持 `Ctrl+Enter` 发送），对方收到后点「复制」即可。

### 配对（跨网络互传唯一的正路）

**两台设备不在同一个网络时，光扫码/开网页是看不到对方的，必须配对。**

1. 一端点顶栏「**配对**」→ 出现 **6 位数字码 + 一个小二维码**
2. 另一端二选一：
   - 扫**那个小二维码**（内容是 `https://<域名>/#pair=<6位码>`，扫开即自动配对）
   - 或点自己的「配对」，手输这 6 位码
3. 配对码 10 分钟内有效、只能用一次；配对关系存在浏览器本地，以后换网络也会自动重连

> **为什么必须配对？** 服务端按**出口 IP** 分房间（这正是"同一个网络自动发现"的原理），
> 电脑走宽带、手机走流量的出口 IP 完全不同 → 天然落进两间房。
> 配对码的作用就是**跨房间把两端拉到一起**。详见**第九节**。

> 注意：配对只在**两台设备都能访问到这个服务**时才有意义。本地版跑在你家电脑上，
> 手机出了 Wi-Fi 就连不上了，所以跨网络配对需要把服务部署到公网（见下文）。

### 公共房间

点顶栏「**房间**」→ 创建一个房间，会得到 5 位房间码。其他人输同一个码就能加入，适合临时拉几个人互传。

## 三、它是怎么工作的

```
   手机浏览器                          电脑浏览器
       │                                   │
       │  ①  WebSocket 连上信令服务器       │
       │     「我是谁 / 谁在线」             │
       │◄──────────── ② 交换 SDP / ICE ─────►│
       │                                   │
       └═══════ ③ WebRTC DataChannel ══════┘
                    文件走这里（P2P）
```

**三个环节：**

**① 设备发现 —— 靠"IP 网段分房间"**

信令服务器按客户端的 IP 把大家分进同一个房间并广播上下线。规则：

| 客户端 IP | 房间 |
|---|---|
| 回环地址（`127.x.x.x`） | **归入本机所在的局域网**，如 `lan:192.168.1` |
| 私网 IPv4（`192.168.x.x`、`10.x`、`172.16-31.x`） | 按 `/24` 聚合，如 `lan:192.168.1` |
| 公网 IPv4 | 每个 IP 一个房间，避免和同 ISP 的陌生用户串台 |
| IPv6 | 按 `/64` 聚合 |

所以同一个 Wi-Fi 下的手机和电脑天然落进同一间房，**这就是"打开网页就互相看见"的原理**——没有任何账号、没有扫码配对、没有 mDNS。

> ⚠️ **回环地址必须归一，这条最容易漏。**
> 你把服务跑在自己电脑上时，电脑浏览器开的是 `http://127.0.0.1:8686`，
> 手机开的是 `http://192.168.1.5:8686`。如果 `127.0.0.1` 被当成一个独立网段
> （`lan:127.0.0`），两端就**不在同一间房**——同一个 Wi-Fi 下反而互相看不见。
> 所以程序会把 `127.x` 映射到本机探测到的那个局域网网段。

**② WebRTC 握手**

服务器只转发 SDP（媒体协商）和 ICE candidate（候选地址），**不接触文件**。握手成功后数据通道直连。

**③ 文件传输 —— 64 KB 分片 + 双重流控**

- 每片 **64 KB**（各浏览器 DataChannel 单条消息上限不一，64 KB 是安全区）
- **水位控制**：发送缓冲超过 4 MB 就暂停，降到 512 KB 继续
- **分区 ACK**：每 8 MB 要求接收端确认一次，防止接收端内存被打爆
- 单条有序可靠通道，天然保证顺序

### 服务器中继兜底（**端到端加密**）

P2P 打不通的场景很常见（路由器 AP 隔离、企业网、某些手机热点）。程序在 6 秒内没建立直连就会**自动切换到服务器中继**，并在界面上明确提示「已切换为服务器中继」——不会偷偷摸摸中转。中继速度慢（base64 + JSON 开销），但一定能通。

**中继通道是端到端加密的。** 这点很重要，因为中继模式下数据会在服务端内存里过一道：

- 两端各自生成一对**临时 ECDH（P-256）**密钥，公钥经中继互换；
- 共享密钥用 **HKDF-SHA256** 派生，数据走 **AES-256-GCM**；
- 服务端全程只搬密文，**看不到文件内容、文件名和文字**（唯一能看到的是公钥）；
- 加密谈不拢（对端是旧版本 / 浏览器不支持 WebCrypto）会自动退回明文，**宁可慢也不让人传不动**，并在界面上如实告知。

> 对比一下：P2P 直连本来就是 DTLS 端到端加密；接 TURN 也只是多一跳中转、中转节点同样只见密文。**只有 WS 中继这条兜底路径**会把明文交到服务端手里，所以专门给它补了这层加密。

### 一台发给多台（多播）

设备列表**可多选**：点卡片选中、再点取消，右上角还有「全选」。发送时会逐个目标并行发一遍。

需要说清楚的是：**这不是真广播，而是 N 份独立的点对点连接**——选 5 台设备，上行带宽就是 ×5。所以合计超过 64 MB 时会先弹一次确认，把代价讲明白再发。

## 四、项目结构

```
flashdrop/
├── start-flashdrop.bat   双击入口（局域网自用）
├── allow-firewall.bat    放行防火墙（可选，需管理员）
├── run.js                启动器：探测局域网 IP、生成自签证书、起 HTTP+HTTPS
├── server.js             信令服务器 + 静态文件（Node 版）
├── public/               ← 前端只有这一份，本地版和线上版共用
│   ├── index.html        页面
│   ├── app.css           样式
│   ├── app.js            界面逻辑（不碰 WebRTC）
│   ├── net.js            传输引擎（信令 / 传输层 / 分片协议）
│   ├── _headers          Cloudflare 响应头（安全头 CSP 等）
│   ├── robots.txt
│   └── vendor/qrcode.js  二维码库（本地，离线可用）
├── cloudflare/           ← 公网部署版（Cloudflare Workers）
│   ├── wrangler.toml     部署配置
│   ├── src/index.js      Worker 入口：路由分流
│   ├── src/room.js       信令 Durable Object（server.js 的移植）
│   ├── src/turn.js       TURN 凭证签发 + 额度闸门
│   └── test/do-sim.js    DO 逻辑离线自测（45 项，不需要云账号）
├── docs/                 部署手册 / 检查报告 / TURN 额度说明
├── certs/                自签名证书（首次启动自动生成）
└── test/                 端到端自测
    ├── e2e.js            基础全流程
    ├── lan.js            电脑 ↔ 手机 · 同 Wi-Fi
    ├── crossnet.js       电脑 Wi-Fi ↔ 手机移动网络
    ├── mobile.js         手机 ↔ 手机 · 同 Wi-Fi（含 iOS 无流式落盘）
    ├── mobile-crossnet.js 手机 ↔ 手机 · 各自不同网络
    ├── relay-fallback.js  P2P 一定失败时的中继兜底
    ├── relay-multicast.js 中继端到端加密 + 多播发送（强制跳过 P2P）
    ├── rename.js          设备改名同步（实时 + 刷新后，两阶段）
    ├── ws-idle.js         信令连接空闲存活性观察
    └── diag-pair.js       同机双浏览器点名互传诊断（房间/连接方式全打出来）
```

分层是刻意的：`app.js` 只把 `net.js` 的事件翻译成界面，所有网络细节都在 `net.js` 里。想改协议只动一个文件。

## 五、配置项

| 参数 | 说明 |
|---|---|
| `--port 9000` | 改端口（HTTPS 自动用端口+1） |
| `--no-tls` | 只起 HTTP（**手机将无法使用**，仅本机调试用） |
| `--no-relay` | 禁止服务器中继兜底（强制只走 P2P） |
| `--trust-proxy` | 信任 `X-Forwarded-For`。**只有放在反向代理后面才开**，直连时开启可被伪造 IP 冒充同房间 |
| `--ignore-reported-addr` | 只按连接地址分房，忽略浏览器上报的出口地址。**默认别开**：双栈网络下正是靠这个上报值，才能让同一张网的两台设备（一台走 IPv4、一台走 IPv6）落进同一间房 |

## 六、已知限制

- **接收端内存**：手机浏览器（iOS Safari）没有 File System Access API，文件只能先攒在内存里再落盘。官方 PairDrop 的经验值是 iOS 上限约 200–400 MB。**大文件建议在电脑端接**——Chrome/Edge 支持时程序会提示选一个保存文件夹，**边收边写盘**，不受内存限制。
- **文件夹**：不支持直接传文件夹，请先压缩。
- **断点续传**：未实现。中断了要重传。
- **多文件不会打包成 ZIP**：一个一个传，每个都能单独看到进度。
- **标签页必须开着**：没有后台接收能力（这是浏览器的限制，不是这个程序的）。
- **公共房间码是弱保护**：5 位码，知道码就能进。别在里面传敏感东西，敏感内容用「配对」。
- **扫码只能发现"同一个网络"的设备**：服务端按出口 IP 分房，所以电脑连 Wi-Fi、手机用流量时，
  扫首页那个大二维码**只会打开网页、不会互见**（二维码里只有网址，不含房间信息）。
  跨网络必须两端各点一次「配对」用 6 位码连接。页面上已有明确引导，详见**第九节**。
- **自签名证书**：浏览器地址栏会显示"不安全"。这是自签名的必然结果，不代表连接没加密——WebRTC 数据通道本身有 DTLS 端到端加密。

## 七、自测

九个脚本，都用**真实 Chrome** 起互相独立的浏览器实例跑完整链路。按真实程度递增：

```bash
# 先启动服务
node run.js

# ① 基础端到端：发现 → P2P 直连 → 发文字 → 双向传文件（SHA-256 比对）→ 流式落盘
node test/e2e.js

# ② 局域网真机场景：电脑开 127.0.0.1、手机开 192.168.1.5:8687（含移动端视口）
#    重点守住「两端必须落进同一房间」这条 —— 同 WiFi 下互相看不见就是这里漏了
node test/lan.js
LAN_IP=192.168.1.5 node test/lan.js

# ③ 跨网络场景：模拟电脑走宽带、手机走移动网络（注入不同来源 IP），
#    验证自动发现失效 → 6 位配对码跨房间配对 → 文件真正送达
node test/crossnet.js

# ④ 两台手机 · 同一个 Wi-Fi：移动端视口 + 移动 UA + 禁用 File System Access
#    （等效 iOS Safari）。验自动发现、P2P、大文件的「纯内存接收」上限提示
node test/mobile.js

# ⑤ 两台手机 · 各自不同的移动网络：配对码跨房间 + 移动端 + 大文件
node test/mobile-crossnet.js

# ⑥ 最坏情况兜底：强制 P2P 一定失败（等效双端运营商 CGNAT）
#    验程序会不会自己降级到中继、降级后文件还完不完整
node test/relay-fallback.js

# ⑦ 落地页文案回归：守住「任意终端 · 任意网络」这个定位
#    防的是"文案退回局域网时代"：首页不能出现"必须连同一个 Wi-Fi"，
#    本地版该补自签证书提示、公网版不该有；
#    另外守住「跨网络扫码看不到对方」时，空状态里必须有明确的配对出路
node test/copy.js

# ⑧ 设备改名同步：① 改完名对端要**实时**更新  ② **刷新本端**后对端仍是新名字
#    只测 ① 会漏 —— 名字只在「改名那一秒」同步过，刷新 / 断线重连后会丢
node test/rename.js
```

## 八、和 PairDrop 的差异

| 方面 | PairDrop | FlashDrop |
|---|---|---|
| 前端 | 需构建（Vite） | 零构建，原生 HTML/JS，改完刷新即可 |
| 房间划分 | 私网 IP 一律改写成 `127.0.0.1`，全部挤一间房 | 按 `/24` 细分，同一服务器下多个内网不会互相看见 |
| 流控 | 每 1 MB 停等一次 ACK | 水位 + 8 MB 分区 ACK 双流控，吞吐更好 |
| 大文件接收 | 全部攒内存 | 支持时**流式写盘** |
| P2P 失败 | 需手动开 `--include-ws-fallback` | 6 秒自动降级并提示 |
| 信令竞态 | 未处理 | 未知设备的信令先缓存，避免偶发连不上 |
| HTTPS | 自己做反代 | 启动时自动生成带 SAN 的自签证书，开箱即用 |
| 文件传输协议 | `request` / `header` / `partition` / `file-transfer-complete` | 同名思路，加了 `file-done` 确保接收端落地后再发下一个 |

## 九、同一个 Wi-Fi vs 跨网络：行为不一样

同一份代码，两种用法差别很大：

| | 同一个 Wi-Fi | 跨网络（手机走 4G/5G） |
|---|---|---|
| 怎么连上 | 打开网页就**自动看见**对方 | 自动看见**失效**，必须用 6 位「配对」码 |
| 为什么 | 两端 IP 落在同一网段 → 同一间房 | 手机是运营商出口 IP、电脑是宽带出口 IP，**不同房间** |
| 传输方式 | 基本都能 P2P 直连，跑满带宽 | 多半打不通，6 秒后退到**服务器中继** |
| 速度 | 快 | 慢（base64 + 中转），且吃服务器带宽 |
| **占用什么带宽** | **只走路由器内部交换，完全不占宽带出口** | 走各自网络出口（**吃家宽上行**），或经服务器中转 |

> **"我家宽带只有几十兆，会不会传得慢？"——同一个 Wi-Fi 下不会。**
> 手机 ⇄ 电脑的数据只经过路由器内部，跟宽带出口（下行/上行）没有关系，
> 上限由 **Wi-Fi 本身**决定：2.4 GHz 常见 3–8 MB/s，5 GHz 能到 20–60 MB/s。
> 只有**跨网络**时才吃家里的宽带，而且主要吃**上行**。

**「配对」怎么用**：电脑点顶栏【配对】→ 显示 6 位码（10 分钟有效、只能用一次）→ 手机点【配对】输入这 6 位码 → 之后长期保持，双方换网络后也能再连上（配对信息存在浏览器本地）。

注意：无论是「自动看见」还是「配对」，牵线都靠**同一台信令服务器**。手机走移动网络要能用，前提是这个服务已经部署到公网。

> **常见困惑：「我扫了首页那个大二维码，手机也打开网页了，但就是看不到电脑。」**
>
> 这正是上面的**跨网络**情况，不是故障。首页那个二维码里**只有网址，不含任何房间信息**；
> 手机打开后，服务端按**它自己的出口 IP** 分房 —— 和电脑不是同一间房，
> 所以「附近设备」一直是空的，看起来就像「扫了没反应」。
>
> 跨网络必须走【配对】，而且**两端各点一次**：
> 电脑点【配对】→ 出现 6 位码 + 一个小二维码（内容是 `https://6.中国/#pair=<6位码>`）→
> 手机扫**那个小二维码**（或手输 6 位码）→ 两端进同一间房 → 互相可见。
> 配对成功后信息存在浏览器本地，以后换网络也能自动重连。
>
> 另外，如果手机**连网页都打不开**（不是"打开了但没设备"），那是另一回事 ——
> 多半是这个域名在手机所在运营商那边还没解析出来，让手机浏览器直接访问一次域名试试。

## 十、部署到公网

**推荐直接上 Cloudflare**（免费、无需运维、自带 HTTPS 与全球加速）。
代码已托管在 **<https://github.com/taichihenry/flashdrop>**，两条部署路线：

- **路线 A（推荐）**：Cloudflare 后台连接该仓库，**Root directory 必须填 `cloudflare`**，
  之后每次 `git push` 自动构建上线
- **路线 B**：本机命令行部署（下面这两条命令）

```bash
cd cloudflare
npm test                  # 离线跑一遍信令逻辑，不需要 Cloudflare 账号
npx wrangler deploy       # 路线 B：本机部署
```

完整步骤见 **`docs/Cloudflare部署手册.md`**（内含本机 `git push` 必须带的代理参数），
上线前的风险清单见 **`docs/上线前检查报告.md`**。

架构：静态资源由 Workers Assets 直接吐（不计费），只有 `/ws` 信令和
`/turn-credentials` 两条路径进 Worker，分别交给 `SignalRoom` 和 `TurnBudget`
两个 Durable Object。前端代码与本地 Node 版**共用同一份**，不存在两套漂移。

> ⚠️ **不能用 Cloudflare Pages 部署这个项目**。Pages 是纯静态托管，
> 不提供 WebSocket 长连接，页面会永远停在「连接中」。必须用
> Workers + Durable Object。

<details>
<summary>其它部署方式（自备服务器 / PaaS）</summary>

1. 丢到任意一台有公网 IP 的服务器（或 render.com / Railway 之类的平台）。
   **别用会休眠的免费层** —— 冷启动 30–60 秒，用户会以为坏了
2. **必须配 HTTPS**：用 Caddy 或 Nginx 挂真实证书（Let's Encrypt）。手机在 HTTP 下拿不到 WebRTC 权限
3. **配 TURN 服务器**：跨网络时两端都在 NAT 后面，只有 STUN 打不通，约 10–20% 的网络环境会永远卡在"连接中"。
   细节（含额度控制）见 `docs/公网部署与TURN额度.md`
4. **反代之后必须开 `TRUST_PROXY=1`**，否则所有访客的 IP 都被记成 `127.0.0.1` 而挤进同一间房、互相可见
   —— 这是安全事故，不是小毛病
5. TLS 交给反代时加 `NO_TLS=1`；ICE 服务器用 `TURN_URL` / `TURN_USERNAME` / `TURN_CREDENTIAL`，
   或直接给 `ICE_SERVERS`（JSON 数组）
6. **另一个部署坑**：若反代和客户端在同一个内网（例如反代装在家里 NAS 上），
   来自公网的访客都会被记成本地地址，同样会串进一间房。必须确保反代透传
   `X-Forwarded-For`（Cloudflare 则是 `CF-Connecting-IP`）

```bash
TRUST_PROXY=1 NO_TLS=1 PORT=8080 \
TURN_URL='turns:turn.example.com:5349?transport=tcp' \
TURN_USERNAME='...' TURN_CREDENTIAL='...' \
node run.js
```

</details>
