# FlashDrop 上线前检查报告

检查日期：2026-10-05
检查对象：`D:\workbuddy\flashdrop\`（前端三件套 + 信令服务 + 测试套件）
上线目标：Cloudflare Workers + 自定义域名 `6.中国`

---

## 一、结论先说

**按原样部署到 Cloudflare 是跑不起来的。** 不是配置问题，是架构不匹配：
Cloudflare Pages 是纯静态托管，**不提供 WebSocket 长连接**，而 FlashDrop 的
"互相发现 + 交换 SDP"这一步必须有一条全双工的常驻连接。

所以这次做的是**把信令服务从 Node 移植到 Cloudflare Workers + Durable Object**，
前端只改了两处（WS 路径、TURN 按需获取），其余协议完全兼容。移植版本见
`flashdrop/cloudflare/`。

除此之外，检查过程中发现 **1 个真实安全漏洞**（Node 版同样中招，已一并修复），
以及若干必须在上线前处理的风险，逐条列在下面。

## 二、🔴 阻塞级问题（不改不能上线）

### 2.1 Cloudflare Pages 无法承载信令服务

| 方案 | WebSocket | 结论 |
|---|---|---|
| Pages（纯静态） | ❌ 不支持 | 页面能打开，但永远停在「连接中」 |
| Pages + Functions | ⚠️ 受限，无法保证同房间落到同一实例 | 房间逻辑会错乱 |
| **Workers + Durable Object** | ✅ 原生支持 | **本次采用** |

**为什么必须用 Durable Object 而不是普通 Worker**：信令是**有状态**的 ——
服务器必须记住"谁在哪个房间""谁该收到哪条 SDP"。普通 Worker 是无状态的，
每次请求都可能是全新的实例，记不住任何东西。Durable Object 才是 Cloudflare
提供的"有状态单实例"原语。

**为什么没有做成"一间房一个 DO"**：FlashDrop 里一个客户端会同时待在多个房间
（自动发现的 `lan:` 房间、公共房间、配对房间），而一条 WebSocket 只能归属一个
DO。拆成多 DO 反而要在 DO 之间来回转发消息。所以改用**全局单实例 DO**承载
房间表，协议与 Node 版逐字一致。

**单实例扛得住吗**：Cloudflare 官方口径是单个 Durable Object 可承载数千条
WebSocket 长连接，软上限约 1000 请求/秒。对当前规模够用。真到瓶颈了，
按房间号做一次哈希分片即可，协议不用动。

### 2.2 信令转发的越权漏洞（已修复）

**问题**：`server.js` 的 `_relay()` 只校验了「房间存在」和「目标在房间里」，
**没有校验发送者本人是否还在这个房间里**。

**后果**：房间标识是可猜的 —— `pub:` 房间码会在用户之间传递，`lan:`/`wan:`
由 IP 直接推导出来。一个**已经退出房间**的客户端，只要还记着对方的 peerId，
就能继续往那个房间里投递伪造的 SDP/ICE，甚至用 `relay` 类型塞入任意数据。

**修复**：

```js
// server.js（Node 版）
if (!room.has(sender.id)) return;

// cloudflare/src/room.js（Worker 版）
if (!room.has(senderWs)) return;
```

两个版本都已修，并补了 3 条针对性测试（见 `cloudflare/test/do-sim.js` 第五节）。

### 2.3 Durable Object 的时长计费会吃穿免费额度

这是最容易踩、且**上线后才会发现**的坑。

Cloudflare 对 DO 的计费包含「时长」：**只要 DO 实例在内存里活着，就按 128 MB
持续计费**。免费额度是 **13,000 GB-s/天**。

算一下：128 MB 的实例常驻 1 小时 = `1 × 3600 × 0.125` = **450 GB-s**。
也就是说，**只需要大约 28 小时**，一个常驻实例就能把一整天的免费额度吃光。
而 WebSocket 信令天然就是常驻连接 —— 用普通的 `accept()`，只要有用户开着页面，
额度就一直在烧。

**修复**：改用 **WebSocket Hibernation API**（`ctx.acceptWebSocket()`）。
休眠状态下的空闲连接不产生时长费用，只有真正收发消息时才唤醒对象。

代价是内存状态会被清空，所以做了两件事兜底：

1. **房间表懒重建** —— 每条 WebSocket 上都用 `serializeAttachment()` 存了它加入
   过哪些房间，需要时用 `ctx.getWebSockets()` 遍历一次就能把房间表完整还原。
   不额外占用 storage，也就不额外产生唤醒。
2. **配对码落 storage** —— 6 位码要活 10 分钟，跨休眠必须持久化，配 `alarm()`
   做过期回收。

同时**删掉了服务端 5 秒一次的 ping 心跳** —— 那会让 DO 每 5 秒醒来一次，
把休眠优化彻底抵消。现在连接存活性交给 Cloudflare 自己处理，客户端靠
`onclose` 自动重连。

### 2.4 TURN 凭证 TTL 必须压到 10 分钟

Cloudflare TURN 按流量计费（$0.05/GB，每月前 1000 GB 免费），
**没有任何硬性封顶**，官方原文：

> Budget alerts are informational only. They do not pause or cap usage.

唯一靠得住的控制点是**签发权在自己手上**。而单条 allocation 的带宽被硬限在
约 100 Mbps，所以单张凭证的理论最坏用量 = `TTL × 100 Mbps`：

| TTL | 单张最坏用量 | 1000 GB 能发几张 |
|---|---|---|
| 48 小时 | 2.16 TB | **一张就击穿** |
| 10 分钟 | 7.5 GB | ~133 张 |

**已固定为 600 秒**，并且在 `TurnBudget` 这个 DO 里做了计数器闸门：
本月已签发张数 × 7.5 GB 超过 900 GB 就不再签发，只回 STUN，
前端自动退回 WebSocket 中继 —— 功能不中断，账单不会超。

## 三、🟠 高风险项（已处理，但你需要知道）

### 3.1 公网 IP 分房有"串房"风险（CGNAT）

原逻辑按客户端 IP 分房：同一个 `/24` 私网落一间房，公网 IP 各自成房。
局域网自用时这是安全的（只有连同一个 Wi-Fi 才同网段）。

**上了公网就不一样了**：国内运营商（尤其中国移动的 4G/5G）大量使用 CGNAT，
**成千上万个互不相干的用户会共享同一个出口 IP**。按 IP 分房意味着这些人会被
放进同一间房、互相看见设备名。

**已做的处理**：

- 留了一个开关 `WAN_ROOM_MODE`：`"ip"`（默认，保住"同一个路由器下自动发现"
  的体验）或 `"off"`（完全不自动分房，只能靠配对码/房间码）。
- 兜底：**接收文件必须对方手动点「接受」**，陌生人最多看到设备名
  （是 `iPhone · Safari` 这种，不含个人身份），发不过来任何东西。

**你需要决定的**：如果这批用户主要在移动网络下使用，建议把
`wrangler.toml` 里的 `WAN_ROOM_MODE` 改成 `"off"`，牺牲一点便利换绝对干净。

### 3.2 页面文案在公网环境下是错的（已修）

首页原来写的是「手机连上**同一个 Wi-Fi**」「首次打开会提示**证书不受信任**」——
这两句在 Cloudflare 部署下全是错的（那里是真证书，也不需要同网段）。
已改为按 `/api/info` 返回的 `mode` 切换文案：

- `mode: "lan"` → 保持原来的局域网引导（本地 Node 版走这条）
- `mode: "public"` → 换成公网引导：「手机扫码打开同一个页面即可互传，不用装
  任何 App」，并说明跨网络用配对码。

### 3.3 没有任何安全响应头（已补）

原本全部依赖浏览器默认行为。已新增 `public/_headers`：

- `Content-Security-Policy` —— 禁止外链脚本、禁止被 iframe 嵌套
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` —— 显式关掉摄像头/麦克风/定位
- `Strict-Transport-Security`

> ⚠️ CSP 是最容易把页面搞白屏的一项。如果上线后发现按钮全失效，
> F12 → Console 会有明确的 `Refused to ...` 报错，
> 把 `_headers` 里 CSP 那一行前面加 `#` 注释掉重新部署即可。

### 3.4 「发送文字」必崩（已修，本轮补测时抓到）

`app.js` 里 `finishActivity(entry)` 少传了第二个参数，而函数签名是
`function finishActivity(entry, { sub, done, level })` —— 解构 `undefined` 直接抛
`TypeError: Cannot destructure property 'sub' of 'undefined'`。

影响面：**任何用户点一次「发送」发文字，页面就抛一次异常**。
文字本身能发出去（发送在前、渲染在后），但活动面板的收尾逻辑被打断。

之所以之前三轮测试全绿却没发现：`e2e` / `lan` / `crossnet` 都只测了文件传输，
**没有一条覆盖「发送文字」这条路**。这轮补 `mobile.js` 时测到才暴露出来。

修法：给第二个参数加默认值 `= {}`（防御性，避免再犯），并补上文字收发的断言。

## 四、🟡 已知限制（本次未处理，先记录）

1. **iOS Safari 不支持流式落盘 —— 已加防护，但天花板绕不过去**。
   `showDirectoryPicker` / `createWritable` 是桌面 Chromium 独有，iOS Safari、
   Firefox、多数手机浏览器都没有。没有它，接收方只能把整个文件攒在 JS 堆里，
   **iOS 单页内存红线约 200–300 MB，越线会被系统直接杀掉标签页**
   （表现是「此网页出现问题，已重新载入」），且无法用 StreamSaver 之类绕过。

   本轮已加**接收前预警**（`net.js` 的 `memoryReceiveLimit()` / `memoryReceiveRisk()`）：
   超线时确认框显示红色警示并建议分批，按钮变「仍然接受（有风险）」；
   未超线但文件大于 64 MB 时提示「请保持页面在前台，不要切走或锁屏」。
   小文件不打扰。**建议写进产品说明：iPhone 单次接收控制在 200 MB 以内。**

2. **WebSocket 中继是全局单实例**。P2P 和 TURN 都失败时才会走到这里，
   此时所有中继流量都压在同一个 DO 上。真出现并发大文件中继会互相拖慢。
   可接受（本来就是个"能用就行"的兜底路径）。

3. **没有速率限制**。单条 WS 消息上限 1 MB（Node 版）/ 由 Cloudflare 兜底，
   但没有对"建连频率""配对码尝试次数"做限制。公网暴露后可能被脚本刷
   （配对码 6 位数字，理论上可暴力枚举；不过单次尝试都要建一条 WS 连接，
   成本不低）。后续可加 Cloudflare Rate Limiting 规则。

4. **国内访问速度一般**。Cloudflare 免费版对中国大陆没有优化线路，
   信令延迟大约在 100–300 ms。信令对延迟不敏感，可以接受；
   但 P2P 打洞的候选交换会慢一点。要提速得买国内节点或换服务商。

## 五、✅ 复查通过的部分

- **路径穿越**：Node 版 `serveStatic` 有 `path.resolve` + 前缀校验；Worker 版
  交给 Assets，不存在文件系统路径概念。
- **文件名注入**：`sanitizeName()` 已过滤 `\0-\x1f <>:"/\|?*` 和开头点号。
- **XSS**：全站没有用 `innerHTML` 渲染任何用户输入。二维码那段 `innerHTML`
  插入的是本地生成的 SVG，数据不超过 URL 本身。
- **房间隔离**：不同网段的设备互相不可见，已用测试固化（第四节）。
- **越权转发**：修完 2.2 后，不在房间里的客户端无法投递任何信令。
- **配对码安全性**：32 字节随机 `roomSecret`（64 位 hex），一次性、10 分钟过期。
- **联系方式**：页脚已按要求加上 `Contact：Email: 153764384@qq.com,
  Mobile: 00 86 13810632766`（`mailto:` / `tel:` 可点）。

### 一次"假回归"的排查记录（值得记下）

第一次复跑 `lan.js` 时第 6 步失败（电脑没弹接收确认框），连跑三次都一样，
一度以为是这次改动引入的回归。加诊断后发现真凶：

```
手机侧诊断：{"sendDone":"ok","state":"connected","kind":"p2p","isOpen":true,
             "pendingText":0,"turnTried":false,"peers":4}
```

**`peers: 4`** —— 传输本身完全正常（`p2p` / `isOpen: true` / `sendDone: ok`），
问题是房间里混进了别的设备。追下去是两件事叠加：

1. 上一次被强制中断的测试留下了**孤儿 Chrome 进程**，仍然连着服务；
2. 机器上常驻的 8686 服务同时被**另一个浏览器**开着（Tabbit）。

测试里 `[...peers.values()][0]` 取的是"第一个设备"而不是"那台电脑"，
于是文件被发给了幽灵。**换成独立端口 + 清掉孤儿进程后，14/14 全过。**

教训：**测试里凡是出现"数量比预期多"的断言失败，先怀疑环境，再怀疑代码。**
而且 `[0]` 这种取值方式本身就是测试的脆弱点。

`do-sim.js` 是自己搭的一套 Durable Object 最小 shim（不做网络、不装 wrangler），
把 `ctx.acceptWebSocket` / `ctx.getWebSockets` / `ctx.storage` /
`ws.serializeAttachment` 按语义实现了一遍，**其中 attachment 做了深拷贝** ——
这一条很关键：真实 DO 每次 `deserializeAttachment()` 都返回新对象，
如果代码改了对象却没写回去，线上会丢状态，而浅拷贝的假 shim 永远测不出来。

> 这套测试第一次跑就抓出了一个真 bug：成员变量 `this._rooms` 与同名方法互相
> 覆盖导致 `TypeError`。如果直接部署，表现是**所有设备加入房间时报错、
> 页面永远显示"还没有其他设备"** —— 属于那种本地看不出来、上线才发现的问题。
