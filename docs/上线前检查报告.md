## 一、结论先说

**按原样部署到 Cloudflare 是跑不起来的。** 不是配置问题，是架构不匹配：
Cloudflare Pages 是纯静态托管，**不提供 WebSocket 长连接**，而 FlashDrop 的
"互相发现 + 交换 SDP"这一步必须有一条全双工的常驻连接。

所以这次做的是**把信令服务从 Node 移植到 Cloudflare Workers + Durable Object**，
前端只改了两处（WS 路径、TURN 按需获取），其余协议完全兼容。移植版本见
`flashdrop/cloudflare/`。

除此之外，检查过程中发现 **1 个真实安全漏洞**（Node 版同样中招，已一并修复），
以及若干必须在上线前处理的风险，逐条列在下面。

## 二、🔴 阻塞级问题（不改不能上线）

### 2.1 Cloudflare Pages 无法承载信令服务

| 方案 | WebSocket | 结论 |
|---|---|---|
| Pages（纯静态） | ❌ 不支持 | 页面能打开，但永远停在「连接中」 |
| Pages + Functions | ⚠️ 受限，无法保证同房间落到同一实例 | 房间逻辑会错乱 |
| **Workers + Durable Object** | ✅ 原生支持 | **本次采用** |

**为什么必须用 Durable Object 而不是普通 Worker**：信令是**有状态**的 ——
服务器必须记住"谁在哪个房间""谁该收到哪条 SDP"。普通 Worker 是无状态的，
每次请求都可能是全新的实例，记不住任何东西。Durable Object 才是 Cloudflare
提供的"有状态单实例"原语。

**为什么没有做成"一间房一个 DO"**：FlashDrop 里一个客户端会同时待在多个房间
（自动发现的 `lan:` 房间、公共房间、配对房间），而一条 WebSocket 只能归属一个
DO。拆成多 DO 反而要在 DO 之间来回转发消息。所以改用**全局单实例 DO**承载
房间表，协议与 Node 版逐字一致。

**单实例扛得住吗**：Cloudflare 官方口径是单个 Durable Object 可承载数千条
WebSocket 长连接，软上限约 1000 请求/秒。对当前规模够用。真到瓶颈了，
按房间号做一次哈希分片即可，协议不用动。

### 2.2 信令转发的越权漏洞（已修复）

**问题**：`server.js` 的 `_relay()` 只校验了「房间存在」和「目标在房间里」，
**没有校验发送者本人是否还在这个房间里**。

**后果**：房间标识是可猜的 —— `pub:` 房间码会在用户之间传递，`lan:`/`wan:`
由 IP 直接推导出来。一个**已经退出房间**的客户端，只要还记着对方的 peerId，
就能继续往那个房间里投递伪造的 SDP/ICE，甚至用 `relay` 类型塞入任意数据。

**修复**：

```js
// server.js（Node 版）
if (!room.has(sender.id)) return;

// cloudflare/src/room.js（Worker 版）
if (!room.has(senderWs)) return;
```

两个版本都已修，并补了 3 条针对性测试（见 `cloudflare/test/do-sim.js` 第五节）。

### 2.3 Durable Object 的时长计费会吃穿免费额度

这是最容易踩、且**上线后才会发现**的坑。

Cloudflare 对 DO 的计费包含「时长」：**只要 DO 实例在内存里活着，就按 128 MB
持续计费**。免费额度是 **13,000 GB-s/天**。

算一下：128 MB 的实例常驻 1 小时 = `1 × 3600 × 0.125` = **450 GB-s**。
也就是说，**只需要大约 28 小时**，一个常驻实例就能把一整天的免费额度吃光。
而 WebSocket 信令天然就是常驻连接 —— 用普通的 `accept()`，只要有用户开着页面，
额度就一直在烧。

**修复**：改用 **WebSocket Hibernation API**（`ctx.acceptWebSocket()`）。
休眠状态下的空闲连接不产生时长费用，只有真正收发消息时才唤醒对象。

代价是内存状态会被清空，所以做了两件事兜底：

1. **房间表懒重建** —— 每条 WebSocket 上都用 `serializeAttachment()` 存了它加入
   过哪些房间，需要时用 `ctx.getWebSockets()` 遍历一次就能把房间表完整还原。
   不额外占用 storage，也就不额外产生唤醒。
2. **配对码落 storage** —— 6 位码要活 10 分钟，跨休眠必须持久化，配 `alarm()`
   做过期回收。

同时**删掉了服务端 5 秒一次的 ping 心跳** —— 那会让 DO 每 5 秒醒来一次，
把休眠优化彻底抵消。现在连接存活性交给 Cloudflare 自己处理，客户端靠
`onclose` 自动重连。

### 2.4 TURN 凭证 TTL 必须压到 10 分钟

Cloudflare TURN 按流量计费（$0.05/GB，每月前 1000 GB 免费），
**没有任何硬性封顶**，官方原文：

> Budget alerts are informational only. They do not pause or cap usage.

唯一靠得住的控制点是**签发权在自己手上**。而单条 allocation 的带宽被硬限在
约 100 Mbps，所以单张凭证的理论最坏用量 = `TTL × 100 Mbps`：

| TTL | 单张最坏用量 | 1000 GB 能发几张 |
|---|---|---|
| 48 小时 | 2.16 TB | **一张就击穿** |
| 10 分钟 | 7.5 GB | ~133 张 |

**已固定为 600 秒**，并且在 `TurnBudget` 这个 DO 里做了计数器闸门：
本月已签发张数 × 7.5 GB 超过 900 GB 就不再签发，只回 STUN，
前端自动退回 WebSocket 中继 —— 功能不中断，账单不会超。

## 三、🟠 高风险项（已处理，但你需要知道）

### 3.1 公网 IP 分房有"串房"风险（CGNAT）

原逻辑按客户端 IP 分房：同一个 `/24` 私网落一间房，公网 IP 各自成房。
局域网自用时这是安全的（只有连同一个 Wi-Fi 才同网段）。

**上了公网就不一样了**：国内运营商（尤其中国移动的 4G/5G）大量使用 CGNAT，
**成千上万个互不相干的用户会共享同一个出口 IP**。按 IP 分房意味着这些人会被
放进同一间房、互相看见设备名。

**已做的处理**：

- 开关 `WAN_ROOM_MODE`：`"ip"`（按出口 IP 分房，保住自动发现体验）
  或 `"off"`（完全不自动分房，只能靠二维码 / 房间码 / 配对码）。
- **已于 2026-10-06 定为 `"off"`**（决策与代价见**第九节**）。理由：兜底那条虽然
  能挡住「收到文件」，但挡不住「被陌生人看见设备名」—— 对一个主打匿名的传输站点，
  这是不能接受的信息泄露，不值得为一点便利去赌。
- 兜底仍在：**接收文件必须对方手动点「接受」**，陌生人最多看到设备名
  （是 `iPhone · Safari` 这种，不含个人身份），发不过来任何东西。

**代价（已接受）**：Cloudflare 侧看到的永远是**公网出口 IP**，所以 `"off"` 之后
**连同一个 Wi-Fi 下的两台设备也不再自动出现**，必须扫一次码。
（传文件依然不出路由器，只是"牵线"这一步从自动变成了扫码。）
本地自建版不受影响 —— 它直连内网、服务端看到私网 IP，`/24` 分房照常工作。

### 3.2 页面文案在公网环境下是错的（已修）

首页原来写的是「手机连上**同一个 Wi-Fi**」「首次打开会提示**证书不受信任**」——
这两句在 Cloudflare 部署下全是错的（那里是真证书，也不需要同网段）。
已改为按 `/api/info` 返回的 `mode` 切换文案：

- `mode: "lan"` → 保持原来的局域网引导（本地 Node 版走这条）
- `mode: "public"` → 换成公网引导：「手机扫码打开同一个页面即可互传，不用装
  任何 App」，并说明跨网络用配对码。

### 3.3 没有任何安全响应头（已补）

原本全部依赖浏览器默认行为。已新增 `public/_headers`：

- `Content-Security-Policy` —— 禁止外链脚本、禁止被 iframe 嵌套
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: strict-origin-when-cross-origin`
- `Permissions-Policy` —— 显式关掉摄像头/麦克风/定位
- `Strict-Transport-Security`

> ⚠️ CSP 是最容易把页面搞白屏的一项。如果上线后发现按钮全失效，
> F12 → Console 会有明确的 `Refused to ...` 报错，
> 把 `_headers` 里 CSP 那一行前面加 `#` 注释掉重新部署即可。

### 3.4 「发送文字」必崩（已修，本轮补测时抓到）

`app.js` 里 `finishActivity(entry)` 少传了第二个参数，而函数签名是
`function finishActivity(entry, { sub, done, level })` —— 解构 `undefined` 直接抛
`TypeError: Cannot destructure property 'sub' of 'undefined'`。

影响面：**任何用户点一次「发送」发文字，页面就抛一次异常**。
文字本身能发出去（发送在前、渲染在后），但活动面板的收尾逻辑被打断。

之所以之前三轮测试全绿却没发现：`e2e` / `lan` / `crossnet` 都只测了文件传输，
**没有一条覆盖「发送文字」这条路**。这轮补 `mobile.js` 时测到才暴露出来。

修法：给第二个参数加默认值 `= {}`（防御性，避免再犯），并补上文字收发的断言。

## 四、🟡 已知限制（本次未处理，先记录）

1. **iOS Safari 不支持流式落盘 —— 已加防护，但天花板绕不过去**。
   `showDirectoryPicker` / `createWritable` 是桌面 Chromium 独有，iOS Safari、
   Firefox、多数手机浏览器都没有。没有它，接收方只能把整个文件攒在 JS 堆里，
   **iOS 单页内存红线约 200–300 MB，越线会被系统直接杀掉标签页**
   （表现是「此网页出现问题，已重新载入」），且无法用 StreamSaver 之类绕过。

   本轮已加**接收前预警**（`net.js` 的 `memoryReceiveLimit()` / `memoryReceiveRisk()`）：
   超线时确认框显示红色警示并建议分批，按钮变「仍然接受（有风险）」；
   未超线但文件大于 64 MB 时提示「请保持页面在前台，不要切走或锁屏」。
   小文件不打扰。**建议写进产品说明：iPhone 单次接收控制在 200 MB 以内。**

2. **WebSocket 中继是全局单实例**。P2P 和 TURN 都失败时才会走到这里，
   此时所有中继流量都压在同一个 DO 上。真出现并发大文件中继会互相拖慢。
   可接受（本来就是个"能用就行"的兜底路径）。

3. ~~**没有速率限制**~~ → **已补（2026-10-06）**。现在有每连接固定窗口限流
   （300 条/秒 + 24 MB/秒，超限断线）、全局连接数闸门（1000，超出回 503）、
   全局房间数闸门（2000）、房间人数上限（配对/扫码 2 · 公共 12 · 自动发现 64）。
   **仍存的口子**：没有对"建连频率"和"配对码尝试次数"做限制 —— 配对码是 6 位
   数字，理论上可枚举，但每次尝试都要新建一条 WS 连接，成本不低。真要收紧，
   建议在 Cloudflare 侧加 Rate Limiting 规则，而不是写进应用代码。

4. **国内访问速度一般**。Cloudflare 免费版对中国大陆没有优化线路，
   信令延迟大约在 100–300 ms。信令对延迟不敏感，可以接受；
   但 P2P 打洞的候选交换会慢一点。要提速得买国内节点或换服务商。

### 一次"假回归"的排查记录（值得记下）

第一次复跑 `lan.js` 时第 6 步失败（电脑没弹接收确认框），连跑三次都一样，
一度以为是这次改动引入的回归。加诊断后发现真凶：

```
手机侧诊断：{"sendDone":"ok","state":"connected","kind":"p2p","isOpen":true,
             "pendingText":0,"turnTried":false,"peers":4}
```

**`peers: 4`** —— 传输本身完全正常（`p2p` / `isOpen: true` / `sendDone: ok`），
问题是房间里混进了别的设备。追下去是两件事叠加：

1. 上一次被强制中断的测试留下了**孤儿 Chrome 进程**，仍然连着服务；
2. 机器上常驻的 8686 服务同时被**另一个浏览器**开着（Tabbit）。

测试里 `[...peers.values()][0]` 取的是"第一个设备"而不是"那台电脑"，
于是文件被发给了幽灵。**换成独立端口 + 清掉孤儿进程后，14/14 全过。**

教训：**测试里凡是出现"数量比预期多"的断言失败，先怀疑环境，再怀疑代码。**
而且 `[0]` 这种取值方式本身就是测试的脆弱点。

`do-sim.js` 是自己搭的一套 Durable Object 最小 shim（不做网络、不装 wrangler），
把 `ctx.acceptWebSocket` / `ctx.getWebSockets` / `ctx.storage` /
`ws.serializeAttachment` 按语义实现了一遍，**其中 attachment 做了深拷贝** ——
这一条很关键：真实 DO 每次 `deserializeAttachment()` 都返回新对象，
如果代码改了对象却没写回去，线上会丢状态，而浅拷贝的假 shim 永远测不出来。

> 这套测试第一次跑就抓出了一个真 bug：成员变量 `this._rooms` 与同名方法互相
> 覆盖导致 `TypeError`。如果直接部署，表现是**所有设备加入房间时报错、
> 页面永远显示"还没有其他设备"** —— 属于那种本地看不出来、上线才发现的问题。

### 7.3 本轮修复：一条过时的断言（非产品缺陷）

`test/mobile.js` 的 `[3] 两台手机同房` 一度失败，但**同一个测试里**两台手机

根因：**扫码房间改造引入了「房间优先级」**。页面级 `signaling.roomId` 现在表示
"当前挑出来发信令的那一间房"，优先级为
`配对(secret) > 扫码会话(session) > 公共(public) > 自动发现(lan)`。
两台手机各自生成扫码房间码、天然不同，所以 `roomId` 本来就不该相等；
它们真正同处的是 `lanRoomId`（按出口 IP 分的自动发现房间）。

`test/lan.js` 早先已修过同类问题，`test/mobile.js` 漏了。已改成读 `lanRoomId`，
复跑后诊断输出直接印证：两台手机的 `lanRoomId` 都是 `wan:120.244.4.3`（同一出口 IP）。

> **教训**：凡是"能互相看见、能传文件"都过了、只有 `roomId` 相等这一条挂，
> 几乎一定是断言读错了字段 —— 因为信令路由走的是 **Peer 自己的房间**（由
> `peer-joined` 事件决定），而不是页面级 `roomId`。这也是为什么 `diag-pair`
> 里两个页面分处不同 `pub:` 房间却能 p2p 直连。

## 八、2026-10-06（第二轮）：STUN 缺失修复 + TURN 决策

### 8.1 本轮抓到的真问题：P2P 的 STUN 在国内等于没有

**症状预期**：跨网络的连接几乎不可能走 P2P，全部静默退化到 WebSocket 中继 ——
用户能用，但慢，而且看不到任何异常提示。

**根因**（两层，缺一不可）：

1. **真正生效的 STUN 是服务端下发的那一份，不是前端的默认值。**
   `public/net.js` 里 `case 'self': this.config = msg.config || this.config;` ——
   信令一连上，服务端下发的 config 就**整个接管**了 ICE 配置。
2. **Node 版下发的 STUN 是两个国内不通的地址。** `server.js` 的 `DEFAULT_ICE`
   只有 `stun.l.google.com:19302` 和 `stun1.l.google.com:19302`。
   这两个在国内都不通 → 等于国内用户的 P2P **完全没有 STUN**，只能收集 host
   候选（本机网卡地址），跨网络时对端根本路由不到。

顺带暴露的第三层问题：**同一份 STUN 列表在三个地方各写一份**
（`public/net.js` / `server.js` / `cloudflare/src/room.js`），且已经漂移 ——
Cloudflare 版有 `stun.cloudflare.com`，Node 版没有；探针函数里又是第三份。

**为什么本地测试测不出来**：本地跑时两端在同一台机器/同一个局域网，host 候选
就能直连，P2P 一次就通，STUN 配没配都"看起来正常"。只有真实跨网络才会暴露。

### 8.2 修复

统一为 `cloudflare → miwifi → google` 三条（顺序不是随意的：ICE 按序尝试，
可达的必须在前）：

| 文件 | 常量 | 改动 |
|---|---|---|
| `public/net.js` | `DEFAULT_ICE_SERVERS` | 新增，并导出到 `FlashDrop.constants` |
| `public/net.js` | `probePublicAddr` | 原来单独写死的 STUN 改为复用同一常量（消灭第四份副本） |
| `server.js` | `DEFAULT_ICE` | 两个 google → 补 cloudflare + miwifi |
| `cloudflare/src/room.js` | `BASE_ICE` | 补 miwifi，去掉冗余的 `stun1.l.google.com` |

计费说明：**`stun.cloudflare.com` 免费且不限量，且不计入 Realtime 那 1,000 GB/月
的计费额度**（计费的只有 TURN 中继的出口流量）。所以这次改动是**纯收益，零成本**。

### 8.3 新增测试：`test/ice-config.js`（16 项）

这类 bug 的特点是**不报错、不告警**：`new RTCPeerConnection()` 不传 `iceServers`
照样能跑，ICE 依然会"成功地"走到 failed。所以必须靠断言守住，做了两层：

- **静态层**：`signaling.config.iceServers` 必须含 STUN、不含 TURN。
- **运行时层**：用 `Page.addScriptToEvaluateOnNewDocument` 在页面脚本执行**之前**
  拦截 `RTCPeerConnection` 构造函数，记录浏览器**真实收到**的 `configuration`
  —— 证明配置真的接到了 WebRTC API 上，而不是躺在某个变量里没人用
  （"配了没接线"是这类问题最常见的形态）。
- **源码一致性层**：直接读三个源码文件、正则抽出 urls 列表比对，把"三份副本漂移"
  钉死。这个项目在 `ROOM_HASH_RE` 和 TURN 上限上都中过"多副本漂移"的招，
  所以宁可写得笨一点。

### 8.4 TURN 决策：暂不注入

**结论：保持不注入。** 三条理由：

1. **不注入 = 账单结构性为零**，不用去判断"这个月会不会超"。
2. **打洞能力已经补齐**（8.2），大量跨网络场景可以直连，用不上中继。
3. **中继实测不慢**：`test/relay-fallback.js` 实测 6 MB 文件走中继 **15.79 MB/s**。

两条必须知道的前置事实（将来真要开的时候）：

- ⚠️ **开通 Realtime TURN 免费套餐需要绑定信用卡**。不绑卡就用不了；
  绑了卡，超出 1,000 GB 免费额度的部分就会**真实扣费**。
  所以"担心被收费"的最优解是**不开**，而不是"开了再把闸门调小"。
- ⚠️ Cloudflare 的额度告警**只是通知**，官方原话
  *"Budget alerts are informational only. They do not pause or cap usage."*
  平台层面**没有硬上限** —— 想做到"绝不付费"只能自己攥住签发权（`TurnBudget` 已实现）。

## 九、2026-10-06（第三轮）：关闭自动发现（`WAN_ROOM_MODE = "off"`）

### 9.1 决策

把 `wrangler.toml` 的 `WAN_ROOM_MODE` 从 `"ip"` 改为 **`"off"`**。

| | `"ip"`（旧） | `"off"`（现在） |
|---|---|---|
| 公网 IPv4 | 每个 IP 一间房，同出口 IP 的用户互相可见 | **不进任何房间** |
| 公网 IPv6（`2000::/3`） | 按 `/64` 聚合 | **不进任何房间**（见 9.4，这个坑是上线后实测才补上的） |
| 私网 IPv4 / 回环 | 按 `/24` 聚合 | **不变**（按 `/24` 聚合） |
| 私网 / ULA / 链路本地 IPv6 | 按 `/64` 聚合 | **不变**（按 `/64` 聚合） |
| CGNAT 串房 | 有风险（移动网络下可能是成千上万人） | **结构性不可能** |
| 同一 Wi-Fi 自动发现 | 可用 | **公网版失效**（CF 侧只看到公网出口 IP） |

### 9.2 代价（这是关键，必须说清）

`off` **不是**"只影响跨网络"，而是**公网版上整套自动发现都没了** ——
因为 Cloudflare 侧看到的永远是客户端的**公网出口 IP**，识别不出"两台设备是否在
同一个路由器后面"。所以：

- 公网版：**一切靠二维码 / 房间码 / 配对码**，包括同一个 Wi-Fi 下的两台设备。
- 传文件依然**不出路由器**（牵上线后 WebRTC 走局域网候选地址），只是"牵线"从
  自动变成扫码一次。
- 本地自建版（`start-flashdrop.bat`）**完全不受影响**：直连内网、服务端看到私网 IP，
  `/24` 分房照常，局域网自动发现照旧可用。

### 9.3 顺带补上的体验缺口（不改代码会很难看）

`off` 之后服务端**不会回任何房间消息** —— 连 `lan-room-full` 都不会回，
因为压根没尝试入房。前端于是只看到一个**空的「附近设备」列表**，没有任何解释，
用户会以为页面坏了（或一直干等一个永远不会出现的设备）。

修法：服务端在 `self` 消息里新增 `config.autoDiscover`，前端据此在空状态里
直接说明「本站已关闭设备自动发现」并给出替代做法（二维码 / 房间码 / 配对码）。

- `cloudflare/src/room.js`：把内联的 config 抽成 `buildSelfConfig(env)` 导出函数
  （服务端与测试共用同一份构造逻辑，避免"服务端改了、测试还绿着"）。
- `public/app.js`：`state.autoDiscoverOff`，`self` 事件里读 `config.autoDiscover`，
  `renderPeers()` 切换 `#lan-off-hint`。
- `public/index.html`：新增 `#lan-off-hint`（与 `#lan-full-hint` 互斥显示）。

Node 自建版不下发这个字段 ⇒ 前端按 `autoDiscover !== false` 处理 ⇒ 默认开启，
行为与改动前一致（这条有断言守着）。

### 9.4 上线后实测抓到的真漏洞：IPv6 绕过了这个开关

**这是本轮最有价值的一条，而且只有真的部署后连一次线上才能发现。**

部署完（Version `3373b15d`）后用真实 WS 连 `wss://6.中国/ws` 复验，`self` 里
`autoDiscover` 确实是 `false`、ICE 也是新的三条 —— 看起来全对。但接着发一条
`join-lan-room`，服务端**仍然回了 `peers`**：

```
peers 详情: {"roomType":"lan","roomId":"v6:2409:8a00:2612:2c90","peers":[]}
```

**根因**：`roomIdForIp()` 的写法是

```js
if (ip.includes(':')) return 'v6:' + ip.split(':').slice(0, 4).join(':');  // ← 在开关之前
if (isPrivateIpv4(ip)) return 'lan:' + ...;
if (wanRoomMode === 'off') return null;                                    // ← 只挡到了公网 IPv4
```

IPv6 分支写在开关**之前**，于是 `"off"` 只对公网 IPv4 生效；
只要客户端走 IPv6（国内移动网络、以及很多家宽现在都是 IPv6 优先），
自动发现**照常把人分进 `v6:xxxx` 房间**。IPv6 的风险跟 CGNAT 是同一类：
运营商常把一整个 `/64` 前缀分给大量用户共享。

**修法**：IPv6 分支里先判公网（`2000::/3`，即首段以 `2`/`3` 开头的 hextet），
公网 IPv6 与公网 IPv4 同等对待；私网 / ULA（`fc00::/7`）/ 链路本地（`fe80::`）
仍然按 `/64` 聚合 —— 局域网自建版正是靠这条才能"打开网页就互相看见"。

**教训（已写进 skill §19）**：
- 「按地址分房」这类逻辑，**每个地址族都要单独确认开关覆盖到了**，
  不能只看了一条分支就以为开关生效；
- 静态检查（`self` 里的字段对不对）**不能替代行为验证** ——
  字段是对的，行为却是错的，本轮就是这种情况；
- 对称的 `if` 链里，"提前 return" 的分支最容易漏掉后置的开关判断。
