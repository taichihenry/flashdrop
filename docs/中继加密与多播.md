## 二、中继端到端加密（核心改动）

### 为什么必须做

| 通道 | 数据对服务端可见性 |
|---|---|
| P2P 直连 | DTLS 端到端加密，服务端不参与 |
| TURN 中转 | 中转节点**只见密文**（DTLS 端点在两端） |
| **WS 中继（兜底）** | **Worker 内存里是明文** ← 唯一的口子 |

产品主打「不存储消息」，但兜底路径上服务端实际进了信任边界。这层加密就是堵它。

### 怎么做的

```
两端各生成一对临时 ECDH(P-256) 密钥
        ↓  公钥经中继互换（服务端看得见公钥，推不出共享密钥）
 HKDF-SHA256 派生 AES-256-GCM 密钥
        ↓
每份数据：第 1 字节是类型标签（0=二进制 / 1=文字），其余是正文
        ↓  AES-GCM 封装：iv(12B) || 密文  → base64
   交给 Worker 转发（它只搬字节）
```

中继消息因此有四种 `kind`：

| kind | 含义 |
|---|---|
| `kx` | 密钥交换，明文，只带公钥 |
| `enc` | 加密数据 |
| `text` / `binary` | 明文（对端不支持加密时的兼容路径） |

### 三个必须处理的细节（都是会静默出错的那种）

1. **加密与解密都必须串行化。**
   `crypto.subtle.encrypt/decrypt` 是异步的，**回调顺序不保证**。并行发出的话文件
   分片会被拼错 —— 而且 SHA-256 照样能过（因为拼进去的字节数对得上），只是内容
   是坏的。所以收发各挂一条 Promise 链严格排队。

2. **双向同时发起协商。**
   两端可能在同一时刻各自生成密钥并互发公钥，所以 `_onKx()` 里也要调 `_startKx()`，
   并且 `_tryDerive()` 在两个位置都要被触发一次（收到公钥时、自己密钥生成完时）。

3. **对端可能比我们更早派生完密钥。**
   对方派生完就会开始发密文，这时我们可能还没好 —— 收到的 `enc` 必须先存进
   `_inbox`，等自己派生完再按顺序解。

### 兼容与降级（宁可慢，不能传不动）

- 对端是**旧版本**（不认识 `kx`/`enc`）：收到明文的 `text`/`binary` 帧即判定，
  当场退回明文并如实提示；
- 浏览器**不支持 WebCrypto**、密钥生成失败、协商超时（4 秒）：一律退回明文；
- **密钥协商是懒触发的**：第一条数据要发时才启动。所以只看界面状态时，
  "还没发过数据的对端"会显示未协商 —— 这是正常的，不是故障。

## 三、顺手抓到的三个真 bug

### 1. 中继通道**完全没有背压**（严重，慢 + 内存尖峰）

```js
// public/net.js:407（修改前）
bufferedAmount() { return 0; }        // ← 注释写着"用它来限速"，但它恒为 0
```

发送循环是：

```js
if (this.transport.bufferedAmount() > BUFFER_HIGH) await this.transport.drain();
```

条件永远为假 → `drain()`（那个 24ms 限速）**在中继模式下从未被调用过**，是死代码。
唯一的背压只有每 8 MB 一次的 `partition` ack。

**修法**：把信令 WebSocket 的真实 `bufferedAmount` 暴露出来，再加上"还没密封完的
字节数"；`drain()` 从固定 sleep 改成**轮询等水位降到 `BUFFER_LOW` 以下**（带 20 秒
兜底超时，防止网络真断了死等）。

### 2. 重复入房 → 房间索引被写进"孤儿 Map"（严重，两端永远看不见）

**现象**：同一间房、双方都不报错，但 `peers` 永远是空的。

**链路**（`server.js:_joinRoom`，修改前）：

```js
const room = this.rooms.get(roomId);        // 拿到 Map 引用
if (room.has(peer.id)) this._leaveRoom(peer, roomId);   // ← 房里只剩它一个时，
                                                       //   _leaveRoom 会把整间房
                                                       //   从 this.rooms 里删掉
room.set(peer.id, peer);                    // ← 写进了那个已经脱钩的 Map
peer.rooms.add(roomId);                     // ← peer 却以为自己进了房
```

最终状态：`this.rooms` 里查不到这间房，而 peer 自己的 `rooms` 里还留着它。
之后所有广播都找不到任何人。

**为什么会重复入房**：`main()` 在信令 socket 还没 open 时就调了一次 `joinLanRoom()`，
而 socket 的 `onopen` 看到 `_joinedRoom` 已为真又重放了一次 → `join-lan-room` 发了两遍。

**修了两处**：

- 客户端（根因）：`joinLanRoom()` 加「同一条连接只排一次」的闸门；`send()` 改为
  返回布尔值，没发出去就把闸门放开，交给 `onopen` 重放。重连时闸门重置。
- 服务端（防御）：`_joinRoom` 里 leave 之后**重新取一次**房间，取不到就新建。

> Cloudflare Worker 版**恰好没这个坑** —— `src/room.js:_join()` 是先 `_leave` 再
> `rooms.has()` 检查并重建，等于天然规避。所以这个 bug 只在**本地 Node 版**
> 表现出来（局域网自用模式会直接废掉）。
> 另外，重复入房在线上也会造成一次多余的 `peer-left` + `peer-joined` 抖动，
> 而抖动正是打断 SDP 协商、把能直连的连接推去中继的元凶之一 —— 这次一并消掉了。

### 3. 拖文件到虚线框会**发送两次**

`drop` 事件冒泡到 `document`，而 document 上还有一个「页面别处也能拖放」的处理器，
两处都调了 `sendFiles()`。修法：在 dropzone 的处理器里 `e.stopPropagation()`。

`test/relay-multicast.js` 里加了断言钉死它（每个目标必须只收到 1 次 `request`）。

## 四、多播发送

设备卡片**可多选**：点一下选中、再点取消，发送面板右上角有「全选」，
面板标题会显示「N 台设备」，下面一行列出具体是哪些。

**它不是真广播，是 N 份独立的点对点发送**：

- 选 5 台 = 上行带宽 ×5；
- 所以合计超过 **64 MB** 时会先弹一次 `confirm`，把代价讲清楚再发；
- 每个 `Peer` 各管自己的发送队列和流控，互不阻塞（并行发）。

界面上的取舍：设备只有一台时仍会自动选中（少点一步）；这一台再点一下就取消 ——
多选语义下这是必要的，`test/{e2e,lan,diag-pair}.js` 里的点卡片动作都已改成幂等。

## 六、已知取舍与遗留

1. **分房依据是客户端上报的出口地址。**
   这是为了解决双栈网络下「同一张网的两台设备一台走 IPv4、一台走 IPv6 被分进
   两间房」的问题（必须由前端用 STUN 探出真实出口地址上报）。
   代价：上报值是**客户端说了算的**，严格隔离要求高的部署可以加
   `--ignore-reported-addr` 退回「只按连接地址分房」。
   `test/{crossnet,mobile-crossnet}.js` 就是用这个开关来模拟不同网络的。

2. **TURN 仍然是关的**。当前链路是「P2P 直连 → 打不通就退 WS 中继」，
   中间那轮「带 TURN 的 ICE restart」会被整段跳过。要开需要去 Cloudflare
   后台建 TURN Key（`docs/部署完成报告.md` 第四节有步骤）。

3. **中继速度仍然慢于直连**（base64 膨胀 + 与信令共用一条 TCP）。
   加密只增加了 ~40 字节/帧，实测吞吐没有可感知变化（5.85 MB/s）。
