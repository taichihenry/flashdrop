# 手机 ↔ 手机 互传能力说明

> 结论先行：**能传**。三种手机之间的组合（同 Wi-Fi / 各走移动网络 / 一 Wi-Fi 一移动网络）
> 都已跑通并留下可复现的测试。
> 但手机端有一条**硬件级的限制**（浏览器内存红线），决定了「能传多大」——
> 这条限制无法用代码绕过，只能如实告知用户。

---

## 一、前提：必须有一个双方都能访问的信令服务器

WebRTC 再"点对点"，也需要一次信令交换（SDP / ICE）才能牵上线。
纯静态页面**做不到**两台手机互传——没有服务器，两边根本不知道对方在哪。

所以顺序是：

1. 先把网站部署到公网（Cloudflare Workers，见 `Cloudflare部署手册.md`）
2. 两台手机各自打开 `https://你的域名`
3. 之后按下面的场景走

> 局域网阶段（电脑上跑 `run.js`）也能让两台手机连上，但用的是自签证书，
> 每台手机都要手动点一次"继续访问"，很折腾。正式用请走公网 HTTPS。

## 二、三种场景对照

| 场景 | 能否互传 | 怎么找到对方 | 数据走哪 |
|---|---|---|---|
| **同一个 Wi-Fi**（含一台开热点、另一台连它） | ✅ 能 | **自动发现**，打开页面就互相出现 | 同一网段内 **P2P 直连**，不经过服务器 |
| **各走各自的移动网络**（两台都不连对方的网） | ✅ 能 | **必须用 6 位配对码**，自动发现一定失效 | P2P 打不通时走 **TURN / 服务器中继** |
| **一台 Wi-Fi、一台移动网络** | ✅ 能 | 同上，必须配对 | 同上 |

### 为什么跨网络就必须配对？

服务端是按**出口 IP 网段**自动分房间的（这是实现"同 Wi-Fi 自动发现"的机制）。
同一个 Wi-Fi 下两台手机都是 `192.168.x.x`，天然同房；
而两台手机各走移动网络时，出口 IP 是运营商分配的，必然不同 →
被分进两间房 → 互相看不见。这时只能靠配对码跨房间牵线。

这不是缺陷，是"既要自动发现、又要不打扰陌生人"的必然取舍。

### 两台手机都在移动网络时，为什么常常要走中继？

国内三大运营商的移动网络普遍是 **CGNAT**（运营商级 NAT）：
手机拿到的不是公网 IP，而是 `10.x.x.x` / `100.64.x.x` 这类共享地址，
STUN 打洞根本钻不出去。这时只有中继能通。

程序的处理顺序是**两段式**，不会一上来就烧中继：

```
无 TURN 试 6 秒  →  失败则取一次 TURN 凭证 + ICE restart，再试 6 秒  →  仍失败才退到 WebSocket 中继
```

好处：能直连的用户一次都不会碰 TURN 额度；真正打不通的那部分又能被救回来。

## 三、手机端的硬限制：能传多大

**这是最需要提前知道的一条。**

| 浏览器 | 接收大文件的方式 | 大致天花板 |
|---|---|---|
| 桌面 Chrome / Edge | 选一个文件夹，**边收边写盘** | 基本不限 |
| **iPhone / iPad 上的所有浏览器** | 只能**全攒在内存**，收完再一次性下载 | **约 200 MB** |
| Android Chrome / Firefox / 其他 | 同上，全攒内存 | 约 1 GB（机型差异大） |

原因：边收边写盘依赖 `File System Access API`（`showDirectoryPicker`），
这个 API **只有桌面 Chrome / Edge 支持**，iOS Safari 和 Firefox 一律没有。
没有它，整个文件必须先攒在 JS 堆里，最后再合成 Blob —— 内存峰值约等于文件大小的 2 倍。

而 **iOS Safari 对单个标签页的内存有硬红线（约 200–300 MB）**，
越线会被系统直接杀掉标签页，用户看到的是「此网页出现问题，已重新载入」——
传输看起来就像莫名其妙失败了，而且**无法用代码绕过**（StreamSaver 之类的流式下载方案在 iOS 上同样会被杀）。

### 已经做的防护

接收确认框现在会**提前如实告知**，而不是让用户传完才发现白忙一场：

- 文件没超安全线 → 提示「文件会先暂存在内存中，请保持页面在前台，不要切走或锁屏」
- 文件超了安全线 → 红色警示「⚠ 超过约 200 MB 很可能导致页面崩溃，建议分批发送，或改用电脑端接收」，
  按钮文案同时变成「仍然接受（有风险）」

判据在 `net.js` 的 `memoryReceiveLimit()` / `memoryReceiveRisk()`。
**小文件（< 64 MB）不弹任何提示**，避免打扰。

### 使用建议

- iPhone 之间互传：**单次控制在 200 MB 以内**（几张照片、一份 PDF、一段短视频都没问题）
- 要传大视频 / 大压缩包：让对方分批发，或者用电脑端接收（电脑能边收边写盘）
- 传输全程**保持页面在前台**，别锁屏、别切到别的 App（切走会被系统冻结，连接会断）

## 四、验证记录

全部为可复现的自动化测试，命令与结果如下（`node test/xxx.js`）：

| 测试 | 场景 | 结果 |
|---|---|---|
| `test/mobile.js` | 两台手机 · 同 Wi-Fi · 均无流式落盘 | **21/21** |
| `test/mobile-crossnet.js` | 两台手机 · 各自不同网络 · 配对码 | **13/13** |
| `test/relay-fallback.js` | P2P 完全打不通（等效双端 CGNAT） | **7/7** |
| `test/crossnet.js` | 电脑 Wi-Fi ↔ 手机移动网络 | 10/10 |
| `test/lan.js` | 电脑 ↔ 手机 · 同 Wi-Fi | 14/14 |
| `test/e2e.js` | 端到端收发全流程 | 18/18 |
| `cloudflare/test/do-sim.js` | Cloudflare Durable Object 信令逻辑 | 45/45 |

关键结论：

- 同 Wi-Fi 两台手机：自动互相发现，走 **P2P 直连**，70 MB 在纯内存接收下也完整送达
- 跨地域两台手机：自动发现如预期失效，**6 位配对码成功牵线**，40 MB 完整送达
- P2P 彻底打不通时：**程序自己降级到中继**，两端状态同步切到 `relay`，文件内容 SHA-256 完全一致

所有文件传输都用 **SHA-256 逐字节比对**，不是"看到进度条到 100%"就算过。

> 测试保真度提醒：这些测试的两个"手机"跑在同一台机器上，
> 因此 P2P 那几条能靠 host 候选直连成功。**真机在 CGNAT 后的表现以 `relay-fallback` 为准**——
> 它专门构造了"P2P 必然失败"的环境，验的就是那条兜底链路。

## 五、上线到 Cloudflare 后，大陆用户的实际体验

1. **Cloudflare 免费版在中国大陆没有节点。** 大陆用户访问会绕到香港 / 日本 / 新加坡，
   延迟通常 100–300 ms，高峰期可能丢包。信令受影响不大，但 **TURN 中继的吞吐会明显打折**。
2. **中继会消耗 TURN 流量额度。** 已做了闸门（凭证 TTL 600 秒 + 900 GB 闸门 + 超额自动退回
   WebSocket 中继），账单锁死 $0，见 `Cloudflare额度与费用边界.md`。
3. **内网直连不受影响。** 同一个 Wi-Fi 下的两台手机走 P2P，不经过任何服务器，也不耗流量额度——
   这是最推荐的使用方式。

---

## 六、一句话总结

两台手机只要能访问到网站，就**一定传得动**——P2P 打不通会自动走中继兜底。
真正要盯着的不是"能不能连上"，而是 **iPhone 上单次别超 200 MB**。
